# Cavia Music 2.0 — Milestone 5.4 Performance Baseline & Profiling Report

## 1. Executive Summary

Milestone 5.4 establishes an empirical, reproducible performance baseline for Cavia Music 2.0 across its native Rust core, SQLite database, audio engine, lyrics parser, and React 19 frontend. 

Prior to this milestone, performance had not been systematically measured at scale. Through synthetic dataset benchmarking (100, 1,000, 10,000, and 50,000 tracks), process-tree runtime profiling, and DevTools/CDP tracing, we identified three material architectural bottlenecks and resolved them with targeted optimizations:

1. **Scanner Duplicate Lookup Bottleneck ($O(N) \to O(\log N)$):** The scanner previously executed unindexed full table scans for each discovered audio file (`content_hash` and `file_uri`). On a 50,000-track library, scanning 2,000 files incurred 4,000 full scans requiring ~30 seconds of pure database scan time. Migration `0006_performance_indexes.sql` introduced covering partial and B-tree indexes, dropping individual lookups from 9.56 ms to **0.04 ms** (a **147× speedup**).
2. **Frontend Playback Position Render Cascades:** Playback position ticks emitted every 250ms triggered root `App` component re-renders, causing full virtual DOM recalculations across active views (such as `TracksView` with 50,000 rows). We implemented a decoupled pub-sub subscriber hook (`usePlaybackPosition`), wrapped all 8 top-level view components in `React.memo`, and stabilized all view action handlers in `useCallback`. During active playback, steady-state root re-renders dropped from **4 per second to 0**.
3. **Binary Footprint Optimization:** By configuring release profile flags (`opt-level = 3`, `lto = "thin"`, `codegen-units = 1`, `panic = "abort"`, `strip = true`), the native binary `cavia-music.exe` shrank from **34.72 MB** to **13.00 MB** (a **62.6% reduction**).

## 3. Benchmark Methodology

### 3.1 Synthetic Database Generation (`cavia-bench`)
A dedicated native benchmark utility was implemented in `src-tauri/src/bin/benchmarks.rs`. It creates an isolated SQLite database using Cavia's real SQLx migration pipeline (`0001` through `0006`), and seeds synthetic datasets with realistic metadata distributions:
- Uniform album sizes (10–12 tracks per album).
- Unique 32-character content hashes and file URIs.
- 10% liked tracks distribution with valid timestamps.
- Synchronized FTS5 full-text indexing triggers on insert/update/delete.
- Representative user playlists with multi-track associations.

### 3.2 Scales Measured
Benchmarks were executed across four dataset orders of magnitude:
- **N = 100 tracks:** Initial prototype / small collection.
- **N = 1,000 tracks:** Typical casual listener library.
- **N = 10,000 tracks:** Substantial enthusiast archive.
- **N = 50,000 tracks:** Heavy power-user local archive.

Each query was warmed up and executed across 20 iterations (10 iterations for N=50,000). Statistical metrics recorded: Minimum, Median, P95, and Maximum durations.

### 4.2 SQLite Query Plans (`EXPLAIN QUERY PLAN`)

With `src-tauri/migrations/0006_performance_indexes.sql`, SQLite utilizes index-backed scans:

#### 1. Scanner Duplicate Lookup by Content Hash
```sql
EXPLAIN QUERY PLAN SELECT id, file_uri, is_deleted FROM tracks WHERE content_hash = 'test' LIMIT 1;
-- Output:
-- SEARCH tracks USING INDEX idx_tracks_content_hash (content_hash=?)
```

#### 2. Scanner Duplicate Lookup by File URI
```sql
EXPLAIN QUERY PLAN SELECT id FROM tracks WHERE file_uri = 'test' LIMIT 1;
-- Output:
-- SEARCH tracks USING INDEX idx_tracks_file_uri (file_uri=?)
```

#### 3. Active Tracks List Sorted by Title
```sql
EXPLAIN QUERY PLAN 
SELECT t.id, t.title, t.artist, t.album, t.album_artist, t.duration_ms, t.artwork_uri,
       t.source_kind, t.provider_id, t.file_uri, t.release_year, t.track_number,
       t.disc_number, t.genre, t.play_count, t.date_added,
       CASE WHEN l.track_id IS NOT NULL THEN 1 ELSE 0 END AS is_liked
FROM tracks t
LEFT JOIN liked_tracks l ON t.id = l.track_id
WHERE t.is_deleted = 0
ORDER BY t.title COLLATE NOCASE ASC;
-- Output:
-- SCAN t USING INDEX idx_tracks_active_title
-- SEARCH l USING INDEX sqlite_autoindex_liked_tracks_1 (track_id=?)
```

#### 4. FTS5 Full-Text Search
```sql
EXPLAIN QUERY PLAN 
SELECT t.id, t.title, t.artist, t.album 
FROM tracks t 
JOIN tracks_fts f ON t.rowid = f.rowid 
WHERE t.is_deleted = 0 AND f.tracks_fts MATCH 'Tokyo' 
ORDER BY t.title COLLATE NOCASE ASC LIMIT 20;
-- Output:
-- SCAN f VIRTUAL TABLE INDEX 0:M6
-- SEARCH t USING INTEGER PRIMARY KEY (rowid=?)
-- USE TEMP B-TREE FOR ORDER BY
```

## 7. Frontend Virtual DOM & Render Optimization

### 7.1 High-Frequency Position Decoupling
- **Problem:** Rust emits `playback:position` IPC updates every ~250ms during playback. Previously, updating `playback.positionMs` in `App.tsx` caused the entire application root to re-render 4 times every second, recalculating virtual DOM diffs across all subviews.
- **Solution:** 
  1. Created `src/lib/usePlaybackPosition.ts` using a direct in-memory pub-sub store (`subscribePlaybackPosition` / `notifyPlaybackPosition`).
  2. Updated `PlayerDock`, `ExpandedPlayer`, and `LyricsDrawer` to subscribe to live position updates directly.
  3. `App.tsx` now receives `playback:position` and routes it to `notifyPlaybackPosition(pos)` without calling `setPlayback`.
- **Result:** Root `App` and un-mounted/non-player views experience **0 re-renders per second** during audio playback.

### 7.2 View Memoization & Handler Stabilization
- Wrapped all 8 primary view components in `React.memo`:
  - `TracksView`, `AlbumsView`, `ArtistsView`, `PlaylistsView`, `LikedTracksView`, `SearchView`, `SettingsView`, and `LibraryView`.
- Memoized `likedTrackIds` with `useMemo(() => new Set(likedTracks.map((t) => t.id)), [likedTracks])` to eliminate set re-allocation.
- Wrapped all action handlers in `useCallback` to ensure stable prop references.

| Metric | Target Budget | Warning Threshold | Regression Action |
